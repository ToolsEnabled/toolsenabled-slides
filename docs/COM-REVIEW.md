# Windows PowerPoint adapter source review

Scope: `scripts/windows/com_host.ps1`, `scripts/windows/export_pdf.ps1`, `scripts/windows/export_thumbs.ps1`, and their Node callers. The plugin selects PowerPoint only on Windows after checking COM registration. Linux/macOS use LibreOffice; the persistent COM host is not started by plugin mode.

The scripts use typed parameters and literal filesystem lookups. Jobs are parsed as JSON rather than evaluated. The persistent host accepts only `thumbs`, validates numeric width and page indices, opens presentations read-only without a window, stages every output, and attempts rollback if promotion fails. The PDF path refuses replacing its source. All acquired COM wrappers are released in finally blocks. A pre-existing PowerPoint instance is not deliberately quit; Quit is conditional on evidence that activation created exactly one new PID. The Node code uses argument arrays and targeted process handling rather than shell interpolation or blanket process kills.

The public plugin API confines source/output paths and supplies private staged paths to these helpers. The scripts are local implementation helpers, not standalone filesystem sandboxes. PowerPoint parses a complex document format; import therefore checks relationship and content types, embedded-object elements and OLE compound-file signatures before a document reaches Office; the rendered package is checked again.

Known limits: PID differencing cannot eliminate every race with another PowerPoint activation; it is conservative when zero or multiple new PIDs appear. COM activation and UI behavior require Windows verification. Headless Linux can test the host protocol, timeout, retirement, PID identity and ownership logic using mocks, but cannot establish actual COM interoperability. Six Python cases use Windows-only COM initialization or native animation/media rendering. `test/windows/export_scripts.test.ps1` parses PowerShell and exercises pure helpers without launching PowerPoint. Actual COM rendering requires desktop PowerPoint and pywin32 for Python COM. Do not infer a Windows runtime qualification from the Linux pass.

The plugin's PowerPoint exports use the one-shot scripts on private files. LibreOffice conversion uses a separate private user profile per job. Both report the chosen renderer and bound subprocess duration. This is an implementation review; an independent security review remains required before release.
